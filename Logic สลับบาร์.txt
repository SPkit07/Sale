ได้ครับ ผมสรุป **Logic ในไฟล์นี้โดยยึดตามเนื้อหาในไฟล์เป็นหลัก** ได้ดังนี้

## ภาพรวมระบบ

ระบบถูกแบ่งเป็น **2 ชั้นหลัก**

### 1. Detection Layer — “ตรวจจับว่าผิดไหม”

เป็น STEP 1 และยังใช้ Logic เดิมทั้งหมด

ใช้:

* Mode
* Median
* MAD
* IQR
* Dynamic Selection
* Robust Z-Score

เป้าหมายคือ **ไม่ตัดสินสาเหตุทันที** แต่ทำหน้าที่เป็นตะแกรงร่อนว่า Import ไหนมีพฤติกรรมผิดจากประวัติของ SKU จนถูกปัก `is_outlier_import = True` 

และ **Import ทั้งหมดที่นำมาคำนวณต้องกรอง Bill ที่ขึ้นต้นด้วย `IB`, `IBK`, `DM`** ก่อน 

---

# 2. Diagnosis Layer — “ผิดเพราะอะไร”

หลังจาก Detection พบ Outlier แล้ว จึงค่อยนำบิลนั้นมาชันสูตร

แบ่งเป็น STEP 2–4

---

## STEP 2 — Dynamic SKU Structure

ระบบต้องพยายามรู้ก่อนว่า SKU มีโครงสร้างหน่วยแบบไหน

เช่น

```text
Master = 30
Inner  = 6
Base   = 1
```

ก็จะเป็น

```text
3-Tier
Master → Inner → Base
30    → 6     → 1
```

แต่ถ้ามีแค่

```text
Master = 30
Base   = 1
```

ก็เป็น

```text
2-Tier
Master → Base
30    → 1
```

### การหา Inner

ไม่ได้เห็นเลขหนึ่งครั้งแล้วสรุปทันที

ต้องดูประวัติ Import ที่ต่ำกว่า Master แล้วใช้ความน่าเชื่อถือของยอดนั้น:

* Ratio ≥ **30%**
* **หรือ** Count ≥ **3–5 ครั้ง** ตามส่วนที่ระบุไว้ใน Logic

เพื่อป้องกัน Noise เช่น มีเลข `6` โผล่มาแค่ 1–2 ครั้งแล้วระบบเข้าใจผิดว่าเป็น Inner Pack 

---

# STEP 3 — Hypothesis + Re-validation

นี่คือหัวใจของระบบใหม่

สมมติระบบเจอ:

```text
Import = 810
```

อย่าเพิ่งบอกว่า “810 คือ 1 ลัง”

ให้สร้าง **หลายสมมติฐาน**

### Hypothesis A — ยิงบาร์ Master ผิด

ถ้า

```text
Master = 30
```

ก็ลอง:

```text
810 / 30 = 27
```

Candidate:

```text
27
```

แล้วเอา `27` กลับไปตรวจ Robust Z-Score กับประวัติเดิม

---

### Hypothesis B — ยิงบาร์ Inner ผิด

ถ้า

```text
Inner = 5
```

ก็ลอง:

```text
810 / 5 = 162
```

Candidate:

```text
162
```

แล้ว Re-validation เช่นเดียวกัน

---

### Hypothesis C — ยิง Base

```text
810 / 1 = 810
```

Candidate:

```text
810
```

---

### Hypothesis D — Double Conversion

กรณีสำคัญที่เพิ่มเข้ามาคือ **คนคีย์หน่วยผิด + ยิง Barcode ผิดซ้ำ**

ตัวอย่าง:

```text
Inner = 12

144 / 12²
= 144 / 144
= 1
```

จึงสามารถค้นพบว่าเจตนาอาจเป็น **12 ชิ้นเดี่ยว** แทนที่จะสรุปง่าย ๆ ว่าเป็น 1 ลัง 

---

# STEP 3.1 — ไม่เลือก Candidate ตัวแรก

นี่เป็นหลักสำคัญมาก

ระบบต้องสร้าง Candidate หลายตัวก่อน:

```text
810
 │
 ├── / Master → 27
 │
 ├── / Inner  → 162
 │
 ├── / Base   → 810
 │
 └── / Inner² → Candidate อื่น
```

จากนั้นเอา **ทุก Candidate ไป Re-validation**

```text
Candidate
    ↓
Robust Z-Score
    ↓
ผ่าน / ไม่ผ่าน
```

ถ้า:

```text
810 → Outlier
162 → Outlier
27  → Normal
```

ระบบจึงมีหลักฐานสนับสนุนว่า:

> **810 อาจเกิดจากการสแกน/บันทึกผิดหน่วย และ Candidate ที่สมเหตุสมผลที่สุดคือ 27**

ตามตัวอย่างในไฟล์ 

---

# STEP 3.2 — Breakdown

เมื่อได้ Candidate ที่ผ่านแล้ว ต้องเอามาแตกกลับเป็นหน่วยหน้างาน

เช่น:

```text
Candidate = 27
Master = 30
Inner = 6
Base = 1
```

คำนวณ:

```text
27 // 6 = 4 แพ็ค
27 % 6  = 3 ชิ้น
```

ดังนั้น:

```text
27 ชิ้น
=
4 แพ็ค
+
3 ชิ้นเดี่ยว
```

ไม่ใช่:

```text
2 แพ็ค + 7 ชิ้น
```

เพราะเศษต้องถูกแตกต่อผ่าน Inner ก่อน 

---

# STEP 3.3 — Typo / Key-in Error

ถ้าเกิดกรณี:

```text
Import = 14
Master = 24
Inner = 6
```

ลอง:

```text
14 / 24 → ไม่ลงตัว
14 / 6  → ไม่ลงตัว
```

และ Candidate ที่เกิดขึ้นก็ยัง **ไม่ผ่าน Re-validation**

ระบบจึงสามารถสรุปเป็น:

> **Typo / Key-in Error**

เช่น มือไปโดนเลขผิด จาก `1` กลายเป็น `14` หรือ `41` 

---

# STEP 4 — Unrecorded Import

อีกสาเหตุหนึ่งไม่ใช่บิลที่ยอดบวม แต่คือ

> **ลืมบันทึกบิลรับเข้า**

ระบบใช้หลัก:

```text
Inbound Gap
+
Negative Stock
+
Max Negative Quantity
```

ตัวอย่าง:

```text
Max Negative = -15
Inner = 6
```

คำนวณ:

```text
ceil(15 / 6)
= 3 แพ็ค
```

ดังนั้น:

```text
3 × 6
= 18 ชิ้น
```

แล้วเอา `18` กลับไปค้นประวัติว่าเคยมี Import จำนวน 18 หรือรูปแบบ 3 แพ็คหรือไม่

ถ้าตรงกัน → หลักฐานสนับสนุนว่า **มีโอกาสลืมคีย์บิลรับเข้า 3 แพ็ค**

## สิ่งที่สำคัญที่สุดจากไฟล์

**Logic เดิมไม่ได้ถูกแทนที่**

มันมีหน้าที่:

> **“บิลนี้ผิดปกติหรือไม่?”**

ส่วน Logic ใหม่มีหน้าที่:

> **“ถ้าผิด แล้วมีหลักฐานว่าเกิดจากอะไร?”**

โดยสาเหตุหลักที่ระบบต้องรองรับคือ

1. **Barcode Swap — Master**
2. **Barcode Swap — Inner**
3. **Double Conversion**
4. **Typo / Key-in Error**
5. **Unrecorded Import**
6. **Duplicate Entry**
7. และ Anomaly อื่น ๆ จาก Detection เดิม

ส่วน **Master / Inner / Base ต้องอิงประวัติ Import จริงของ SKU** และต้องมีเกณฑ์ความน่าเชื่อถือ ไม่ใช่เดาจากเลขใดเลขหนึ่งเพียงอย่างเดียว 

**จุดนี้สำคัญมาก:** ในไฟล์มีทั้งแนวคิด `Count ≥ 3` และช่วงหนึ่งระบุ `3–5` ครั้ง ดังนั้นถ้าจะเอาไปล็อกเป็นโค้ด production ควรถือว่า **threshold นี้เป็น parameter ที่ปรับได้** ไม่ควร hard-code แบบตายตัวจนแก้ไม่ได้ครับ.
